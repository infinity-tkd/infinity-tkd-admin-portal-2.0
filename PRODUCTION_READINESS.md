## Changes implemented

- Fresh active account checks and permission overrides now protect server operations. Anonymous username-to-email lookup and browser fallbacks that granted Admin authority were removed. Old stock/order functions lose client execution rights. Auth signup metadata cannot grant staff authority.
- User permission reads are restricted to the caller or Root. Changing a batch of user overrides uses one audited database transaction. Private operational tables honor their read or write permissions; teaching resources and published schedules remain readable by active accounts.
- New staff accounts receive unique random passwords and must change them before using the portal. Password changes are independent of profile edits. Removing the final active Root account is blocked. Archiving accounts and students preserves their history.
- POS prices come from the database catalog. Orders, line items and inventory movements share a transaction; stock cannot be oversold or silently clamped. Retry keys prevent duplicate checkout. Cancellation restores reserved inventory once. A refund requires an operator's verified external reference; it does not execute a bank refund.
- Catalog edits preserve variant IDs and reject destructive changes to stocked or reserved variants. Student creation, profile/address edits, household saves and account provisioning use database transactions.
- Partner edits, creation and deletion require confirmed database results. Sample-record and failed-schema success fallbacks were removed; the API uses the installed modern CRM schema without silently dropping MOU fields. Partner lists load all pages, invalid IDs and dates are rejected, and expiry cannot precede the signing date.
- Clearing modern CRM contacts or notes no longer resurrects duplicated legacy values. The SQL upgrade carries legacy secondary contacts into modern fields before switching reads to the modern values.
- Tuition uses configurable standard/early-group fees, academy calendar dates and capped enrollment anniversaries. Older unpaid cycles remain visible. Renewal collection targets the actual due month. Immutable transactions provide real receipt numbers; batch allocations roll back together and settled months cannot be overwritten. Positive payments must equal the full current tuition; partial payments and excess payments are rejected. Explicit zero-value waivers remain supported for authorized finance staff.
- Family tuition collection now records one outstanding cycle per active sibling in a single audited transaction. A permanent family receipt stores the guardian, method, verified external reference and individual allocation receipts. Retries return the same receipt. Non-cash collection requires staff verification of received funds; no bank transfer is initiated by this screen. Missing/paused/inactive links, changed tuition amounts and duplicate bank references roll back the whole batch. Family batches are included in application-data exports.
- Measurements and the student's latest height/weight commit together, with retry keys and a trusted recorder. Past measurements cannot overwrite newer metrics; zero optional measurements are preserved. Invalid numbers/dates fail validation.
- Student profile and primary-enrollment-date edits share one transaction. Failed saves propagate to callers. Contact email updates keep the login identity unchanged; pausing training does not locally simulate account suspension. Settings and workout forms keep their data when a save fails. Academy settings no longer use an unconfirmed direct-write fallback or display a local-only successful save.
- Library assets, muscle relations and matching curriculum records commit together. New IDs avoid existing curriculum rows; conflicting legacy IDs are blocked for manual reconciliation. Deleting a lesson with student progress is blocked. Watch-status changes retain the target belt and prior progress metrics, use trusted permission checks, and write an audit event. A completion reset retains the progress row instead of deleting its history.
- Student, staff and library imports support multiline CSV, a 2 MB/500-row limit, paced requests, row-error CSV downloads and retrying failed rows without replaying confirmed saves in the current open wizard. Resume state is in memory; closing/reloading the wizard loses it. For ambiguous network/account-provisioning failures, check the directory before retrying. Staff credential downloads contain only confirmed accounts.
- The reported script-nonce hydration warning is fixed on the two affected scripts. Browsers hide the content attribute while retaining the `script.nonce` property ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/nonce#accessing_nonces_and_nonce_hiding)); script-local hydration suppression handles this expected browser behavior. The CSP nonce is retained. A real browser verified three pages plus a dark-theme reload in both development and production with no hydration/page errors and nonce values matching CSP.
- Attendance records distinguish each class on the same date. Creating an absent roster preserves prior check-ins; selected-class marks and resets affect that class. Existing date-only records remain legacy daily records.
- Class capacity counts active, unarchived students. Inactive enrollments do not occupy capacity; reactivation is rejected when the class is full. Class edits cannot reduce capacity below active enrollment, invert the merged start/end times, or assign an inactive coach.
- Promotion and void operations synchronize the current belt inside the history transaction. A starting rank is captured for students with no prior history. Existing students with history default to White as their baseline; review migrated advanced ranks on staging before allowing deletion of their final history record.
- Initial data and order history are paginated. Query failures are surfaced instead of silently returning a complete-looking partial ledger. Sensitive student and POS caches were removed. Protected navigation is network-only; PWA upgrades require a deliberate reload.
- A nonce CSP replaces conflicting policies. Image redirects are checked at every hop and response size is bounded. Request bodies are bounded. Untrusted CSV text is quoted and protected against spreadsheet formulas; staff/student import parsing handles quoted multiline fields.
- Type and lint checks are enforced in the build. The quality workflow runs type checking, lint, regression tests, runtime dependency audit and production compilation.
- Reads use bounded concurrency, timeouts and cancellation when sessions change. Realtime events trigger debounced canonical reads, preserving joined addresses and receipt metadata. Visible tabs reconcile after reconnecting and every 60 seconds; hidden/offline tabs pause this recovery. Failed reads remain visible and can be retried.
- Automatic SDK retries are disabled for writes, including non-idempotent RPCs. Safe paginated GET reads explicitly opt into retries. POS submission also prevents concurrent checkout, retains retry keys and excludes pending, refunded, void and cancelled orders from collected revenue.
- Runtime failures use privacy-filtered, rate-limited telemetry. Error reporting cannot recursively crash the UI. Failed saves do not promise offline synchronization or show unconfirmed success.

## SQL code

`supabase/production-upgrade-20261009.sql` contains the nine baseline upgrade migrations through `20261011090200_portal_validate_existing_records.sql` in one transaction. Regenerate that baseline bundle after editing its migrations with:

```powershell
node scripts/build-sql-upgrade.mjs
```

Use the baseline bundle **or** its nine individual migrations, according to the installation's migration history. Do not apply both. Policy and constraint creation is not a repeatable maintenance script.

The separate follow-up [20261011215930_portal_realtime_sync.sql](supabase/migrations/20261011215930_portal_realtime_sync.sql) is deliberately outside that baseline bundle. Apply it after the baseline on other installations. It adds missing RLS-protected tables to `supabase_realtime`; it changes no business rows, grants or policies. The connected Infinity TKD project already has both upgrades. For partially upgraded installations, apply only their missing migrations in chronological order after rehearsal; reapplying the complete bundle can conflict with existing policies and constraints.

## Operational limits and further work

- Automated bank refunds, provider webhook verification, partial payments, credits, tuition pause/proration rules and historical rate snapshots still need business rules and provider integrations. The supported collection workflow records complete monthly tuition or an explicit individual waiver.
- Application-data exports are not provider backups. Automated provider backup/restore drills, centralized alerting, telemetry retention, load testing, keyboard/screen-reader testing and real device PWA/browser testing remain release operations.
- PostgreSQL transactions cannot include Supabase Auth. Email/profile failures attempt to restore the original Auth email and explicitly report reconciliation failures. Provisioning compensates by removing a newly created Auth identity when database provisioning fails, and reports the account ID for administrator reconciliation if cleanup also fails. Monitor these distributed failures and do not assume provider outages are atomic.
- The store and several screens are large. Unused-code and image-optimization lint warnings are tracked rather than suppressed; incremental decomposition and performance measurement remain worthwhile.
