Infinity Taekwondo Admin Portal — System Review
Review date: 9 October 2026

This records the findings before the repair work. For implemented fixes, current verification results and remaining release requirements, see `PRODUCTION_READINESS.md`.

The portal has substantial functionality and useful foundations: authenticated API handlers, active-account checks, Zod validation, RLS migrations, realtime updates, error boundaries, responsive layouts, translations, and lazy-loaded anatomy views. The most valuable next work is to make permissions, financial records, stock, and success messages trustworthy across all paths.

This is a source-code and local-tooling review of the current checkout. It covers authentication, staff/student accounts, permissions, dashboard, directory/dossiers, households, attendance, scheduling, financials, POS/shop, LMS/library/anatomy, partners, settings, PWA, API handlers, database migrations, and operational tooling. No live database policies, storage permissions, hosting configuration, production browser sessions, or payment-provider accounts were inspected. No production writes or exploitation attempts were made. Database findings describe the SQL committed here; live exposure depends on which migrations and grants are installed.

**Validation performed**

- TypeScript: `npx tsc --noEmit --incremental false` passed.
- Repository lint: `npm run lint` failed with 68 errors and 33 warnings, including the reference project in CloneIntegrate.
- Application-only lint: 63 errors and 32 warnings across app, components, hooks, lib, middleware.ts, next.config.ts, and sw.ts. These are static rule findings, not 63 demonstrated runtime failures.
- Production dependency audit: `npm audit --omit=dev --json` reported six affected package entries: five high and one moderate; no critical entries. Entries include transitive relationships and are not six independently exploitable portal vulnerabilities. Packages flagged: @serwist/next, browserslist, next, nested postcss, sharp, and source-map-js. npm reports fixes available; the proposed Next remediation is a major upgrade and needs compatibility validation.
- Installed versions checked: Next 15.5.27, React 19.2.6, @serwist/next 9.5.12. README badges describe older versions.
- Date probe: under Asia/Bangkok, local 9 October 2026 at midnight and 06:30 both become `2026-10-08` when formatted with `toISOString().split('T')[0]`.
- Source scan did not find the scanned common credential-token patterns outside the excluded local environment file, dependencies, generated build, and lockfile. This is not a complete secrets/history audit.

**Urgent security and correctness findings**

1. **Critical if deployed as written — protect database functions themselves.** The POS/order/inventory functions run as SECURITY DEFINER without sufficient caller permission or student-ownership checks. `confirm_student_order` and `cancel_or_refund_order` are explicitly executable by authenticated users; the later stock/sale/order functions have no explicit execute revocations in this repository. A caller able to execute them directly through Supabase can bypass the Next API's role checks. Revoke public/anonymous execution, allow only required roles, verify identity and effective action permissions inside functions, and pin search_path. Evidence: supabase/migrations/20260913_student_account_linking_and_rls.sql:492 and :533; supabase/migrations/20260930_proshop_product_variants_and_matrix.sql:34, :136, :293. Supabase documents that definer functions can bypass RLS and that execution is broadly allowed by default: https://supabase.com/docs/guides/database/functions

2. **Critical/High, dependent on live grants and registration — close profile escalation and ownership gaps.** The master profile INSERT policy allows `auth.uid() = id` without restricting the requested role or student link. Profile UPDATE permits administrators broadly and protects only role/is_active on the self-service path, leaving ownership-sensitive fields such as student_id/username insufficiently constrained. Ownership helpers accept those fields, email, and username variants. The API's stronger field/hierarchy checks do not protect direct table writes. Separate ordinary profile fields from protected role/account-link fields; create trusted provisioning and linking operations. Evidence: supabase/migrations/20260928_master_defense_in_depth_rbac.sql:180, :274, :296; app/api/admin/update-user/route.ts:101.

3. **High — enforce the configured permission matrix in APIs and SQL.** Role/user permission tables mainly affect frontend `can()` decisions; `verifyCaller` only checks role and active status. For example, a Coach is accepted by student-update and POS endpoints even though baseline matrix actions deny those operations; Admin/Head Coach can call student deletion despite their baseline deny. Revoking a button does not revoke the underlying API capability. Use one effective-permission resolver across UI, API, direct writes, and RPCs; include branch/resource scope where the academy requires it. Evidence: lib/backend-security.ts:112; app/api/admin/update-student/route.ts:63; app/api/admin/delete-student/route.ts:18; app/api/admin/pos/orders/route.ts:11; supabase/migrations/20260928_dynamic_role_permission_matrix.sql.

4. **High — remove shared account passwords.** Bulk staff import supplies no password, and `addUser` substitutes one fixed password for every such account. Use invitation/reset links or unique temporary credentials with an enforced first-login reset. Review and reset existing accounts created through this path. Evidence: components/BulkImportStaffModal.tsx:461; lib/store.tsx:3300.

5. **High — make Logout All Devices actually revoke sessions.** The account panel contains sample device/location/IP entries; its logout action filters local React state and shows a success message without an authentication operation. Connect the action to real session revocation, show only verified session information, and explain any access-token expiry delay accurately. Evidence: components/AccountSecurityPanel.tsx:49 and :69.

6. **High — fail closed when the profile cannot be verified.** On a missing/failed profile lookup, the interface falls back to user-editable metadata and then Admin, with active status defaulting to true. Backend `verifyCaller` is stricter, so this is not proof of universal backend Admin access, but it exposes an incorrect privileged UI and combines badly with database weaknesses. Require a verified, active staff profile before rendering protected content; cached UI permissions must not be authoritative. Evidence: lib/store.tsx:715 and :1182.

7. **High privacy concern if deployed — restrict anonymous profile and permission reads.** The master SQL allows anonymous SELECT of all profiles; individual permission overrides are also readable by anon with USING true. Profiles include email, username, role and student links. The unauthenticated username endpoint and anonymous username RPC disclose email addresses and distinguish account states. Limit reads to self/authorized staff, remove public override visibility, and resolve username login server-side with generic failures. Evidence: supabase/migrations/20260928_master_defense_in_depth_rbac.sql:266; supabase/migrations/20260928_dynamic_user_permission_overrides.sql:42; app/api/auth/username-to-email/route.ts:85; supabase/migrations/20260913_student_account_linking_and_rls.sql:309.

8. **High — repair the student-shop API/SQL contract.** The API sends product_id, variant_id, size and qty. The latest order-placement function expects price, sku, name and color too, including price during subtotal calculation. Missing fields can produce null totals or line-item failures, depending on installed schema. The API fallback uses base product prices and ignores variant overrides. Define one versioned contract and derive all authoritative prices and descriptions inside the transaction from product/variant records. Evidence: app/api/shop/order/route.ts:154; supabase/migrations/20260930_proshop_product_variants_and_matrix.sql:313 and :362.

9. **High — remove unsafe POS/shop write fallbacks.** Any RPC error switches into separate order, item and stock writes. These writes can succeed partially; some returned errors are ignored, and a rejected transaction can be bypassed by the fallback. Return the original failure and fix the transaction rather than declaring success after partial writes. Evidence: app/api/admin/pos/orders/route.ts:167; app/api/shop/order/route.ts:175.

10. **High — calculate POS amounts on the server.** The counter-sale API accepts caller-supplied price, subtotal and product labels; the SQL trusts them. Recalculate line prices and totals from approved catalog/variant data, validate product/variant relationships and active status, and make price overrides a separately authorized, audited operation. Evidence: app/api/admin/pos/orders/route.ts:14 and :142; supabase/migrations/20260930_proshop_product_variants_and_matrix.sql:162 and :223.

11. **High — reject insufficient stock rather than clamping to zero.** SQL uses GREATEST(0, stock - quantity), so selling beyond stock still appears successful. Fallback reads/updates also race between cashiers. Use atomic availability checks with locks/conditional updates, aggregate repeated cart items, and keep parent/variant stock consistent. Evidence: supabase/migrations/20260930_proshop_product_variants_and_matrix.sql:250 and :265; app/api/admin/pos/orders/route.ts:221.

12. **High — make cancellation match actual stock reservations.** The latest student order-placement function inserts pending orders without deducting/reserving stock. Cancellation nevertheless adds every order item's quantity back to stock. Cancelling such an order can inflate inventory. Confirmation permits arbitrary status updates without a transition graph, and cancellation labels paid orders REFUNDED without recording proof of an external refund. Track reservations explicitly, restore only reserved/deducted quantities, require valid transitions, and separate cancellation from completed refund reconciliation. Evidence: supabase/migrations/20260930_proshop_product_variants_and_matrix.sql:293; supabase/migrations/20260913_student_account_linking_and_rls.sql:510 and :555.

13. **High — stop reporting payments as saved when they failed.** `payInvoice` and bulk prepayment catch failures and return normally; callers then show success. Some handlers do not await the write at all. Return a structured success/error result and display success/receipts only after a confirmed committed payment. Evidence: lib/store.tsx:1974 and :2024; components/FinancialsView.tsx:1097, :3698, :4209.

14. **High — persist households and family checkout.** Household data starts with a hardcoded guardian and the first two students. Creating/linking/removing households only changes local state, and checkout constructs a receipt without recording family payments. Persist households, guardians, student links and allocations in the database; remove sample data from operational UI. Evidence: components/HouseholdManagementModal.tsx:43, :105, :164.

15. **High — make multi-record creation, updates and deletion transactional.** Student/user handlers separately write profiles, addresses, enrollments and linked records, often without checking every error. Student deletion removes child records before knowing whether the parent delete succeeds. Auth creation/deletion also needs compensation/reconciliation because it crosses service boundaries. Archive students by default, transactionally change related database rows, and explicitly handle Auth failures. Evidence: app/api/admin/create-student/route.ts:175; app/api/admin/create-user/route.ts:206; app/api/admin/update-student/route.ts:143; app/api/admin/delete-student/route.ts:56; app/api/admin/delete-user/route.ts:111.

**Reliability, privacy and operational improvements**

16. **High — load complete, scoped data instead of all-table snapshots.** Login makes 24 broad queries, many using select('*') with no pagination. Default API row limits can silently truncate students, attendance, payments and histories, making reports and billing incomplete. Load data by module, branch and date with pagination; use database aggregates for authoritative dashboard totals. Show explicit unavailable/partial states instead of converting query errors into apparently empty tables. Evidence: lib/store.tsx:741.

17. **High — use a reliable billing and payment ledger.** Dashboard/financial views return no enrollment date for students without class enrollment, while the shared billing helper falls back to registration. Missing enrollment is treated as before every billing month in other views. Fees are hardcoded to $25/$45 across several places; payments upsert and overwrite a monthly row instead of representing immutable payments/allocations. Centralize plan/effective-date rules and support partial payments, credits, waivers, pauses, refunds and outstanding balance. Evidence: components/FinancialsView.tsx:24 and :43; components/DashboardView.tsx:96; lib/store.tsx:1974 and :4366; components/HouseholdManagementModal.tsx:79.

18. **High — fix academy-local dates and billing anniversaries.** ISO UTC slicing is used for daily attendance, enrollment and billing display alongside local calendar calculations. This can record the previous day before 07:00 in Cambodia/Bangkok. The enrollment-minus-one-day billing anchor also needs explicit handling for day 1 and month-end dates. Use a single academy timezone/date-only representation and verify leap years, month ends, first-of-month enrollments and year rollover. Evidence: components/DashboardView.tsx:140; lib/store.tsx:2689 and :4387; local date probe above.

19. **Medium/High — tie receipts to saved payment records.** Opening a receipt generates a new random transaction reference; payment method, reference and custom receipt settings are independent UI state. Save to Admin is a timer-based success animation. Store immutable receipt/payment IDs, real collection method, amount, collector and timestamp; reprint from that record. Evidence: components/FinancialsView.tsx:136 and :149.

20. **High — protect attendance from multi-class and concurrency errors.** Attendance is keyed only by student/date although scheduling supports multiple classes. Bulk absent marking filters a client snapshot, then upserts Absent, which can overwrite a check-in made by another staff member after the filter. Record attendance per actual class occurrence and make absent finalization insert-only or conditional. Roll back only the failed record, rather than replacing an entire array that may contain later successful changes. Evidence: lib/store.tsx:1893 and :3356.

21. **Medium/High — enforce enrollment capacity and identifiers on the backend.** Class capacity is checked against local state before an ordinary insert; simultaneous enrollments can overfill a class unless untracked live triggers prevent it. The initial-class enrollment path does not repeat this check. Student IDs are generated from loaded array length, creating collisions after deletions, truncated reads or concurrent registrations. Use an atomic enrollment operation and a database-backed identifier allocator. Evidence: lib/store.tsx:2095 and :2665; components/BulkImportStudentModal.tsx:540; app/api/admin/create-student/route.ts:188.

22. **High — make the audit trail accurate and harder to forge.** Audit insert errors are not inspected because Supabase normally returns errors rather than throwing. The SQL permits authenticated clients to insert arbitrary audit entries with WITH CHECK true. Anonymous crash telemetry writes into the same table. Restrict sensitive event writes to trusted server/database paths, bind actor identity, separate telemetry from security history, and alert on logging failures. Evidence: lib/backend-security.ts:348; supabase/migrations/20260928_master_defense_in_depth_rbac.sql:789; app/api/telemetry/log/route.ts:90.

23. **High — make account suspension and permission revocation effective promptly.** RLS helper functions prefer role/is_active in issued JWT app_metadata, which can remain stale after a profile change. The API reads current profiles, creating different revocation behavior between API and direct database requests. Define revocation expectations, consult current trusted account state for sensitive actions, and test existing-token behavior after suspension/demotion. Evidence: supabase/migrations/20260928_master_defense_in_depth_rbac.sql:103 and :117.

24. **Medium/High — minimize and isolate browser caches.** Student records/body data are stored using XOR with a constant bundled key; this is reversible obfuscation. POS sale records persist under global localStorage keys, and LMS grades also remain in localStorage. Namespace any permitted cache by account/academy, clear sensitive records on logout, minimize medical/contact data, and treat cached state as untrusted. Store pending offline changes explicitly with synchronization status rather than presenting unsaved grades as final. Evidence: lib/store.tsx:16 and :1254; components/InventoryPosView.tsx:131 and :740; components/LmsView.tsx:949 and :963.

25. **Medium — harden API resource limits and image fetching.** JSON is fully parsed before length/schema validation; arrays have no meaningful upper bounds on some routes. Rate limits use process-local Maps and caller IP headers, so protection depends on trusted proxy normalization and instance topology. The image proxy validates only the initial URL, follows redirects, reads the full response before checking actual size, and clears its timeout after headers rather than body completion. Add shared limits where required, request/array caps, validated redirect destinations, streamed size ceilings and whole-transfer timeouts. Evidence: lib/backend-security.ts:43 and :250; middleware.ts:79; app/api/image-proxy/route.ts:129.

26. **Medium — consolidate security headers and origin rules.** Both middleware and next.config define different CSPs; both allow unsafe-inline/unsafe-eval, and next.config allows broad connect-src schemes. Localhost origins are accepted regardless of deployment environment. Use one effective production policy with verified allowed destinations, nonce/hash scripts where feasible, and configured production origins. The global Permissions-Policy blocks camera access, so a future browser QR scanner needs an intentional camera policy. Evidence: middleware.ts:21 and :62; next.config.ts:102.

27. **Medium — prevent spreadsheet-formula injection in exports and strengthen imports.** Partner CSV export escapes quotes but leaves formula prefixes intact. Student CSV parsing splits physical lines before parsing, so quoted multiline fields are not correctly represented. Imports run one account/student request per row, which can hit the portal's 60-request route limit and only give limited failure recovery. Use a robust CSV parser, formula-safe exports, server batch jobs with bounded pacing, and downloadable row-level failures/resume support. Evidence: components/PartnersView.tsx:316; components/BulkImportStudentModal.tsx:161, :381, :542; components/BulkImportStaffModal.tsx:458; middleware.ts:86. OWASP describes formula injection risk: https://community.owasp.org/attacks/CSV_Injection

28. **Medium/High — repair React correctness issues first.** `ManageStudentPanel` returns early when its student is missing, then declares another useState later, violating hook ordering. `DirectoryView` assigns directly to context state instead of using store updates. Unify belt-history edits through one store action and keep all hooks unconditional. Treat remaining lint findings according to impact; many are style/compiler-compatibility warnings rather than demonstrated bugs. Evidence: components/ManageStudentPanel.tsx:360 and :582; components/DirectoryView.tsx:140; application lint report.

29. **Medium — stop substituting invented dashboard metrics.** When attendance data is empty, the dashboard returns fixed Saturday 89% and Monday 64% figures. Show No data/Unavailable, distinguish query failure from empty history, and label forecasts/heuristics with their assumptions and sample size. Evidence: components/DashboardView.tsx:178 and :199.

30. **High operational priority — make release checks meaningful.** next.config disables build failure on TypeScript and ESLint errors. The default lint also includes CloneIntegrate, creating unrelated noise; eslint-config-next is a different major from Next. Fix the confirmed correctness issues, define intentional lint scope, align tooling, and require typecheck/lint plus critical workflow tests in CI. No formal application test runner or CI workflow was found; scratch database scripts are not equivalent. Evidence: next.config.ts:10; eslint.config.mjs; package.json; tsconfig.json.

31. **High operational priority — remediate dependency advisories with compatibility testing.** Update the flagged dependency graph, verify actual reachability and production/build usage, and re-audit the lockfile. Do not apply a forced major upgrade blindly. Validate PWA generation, image optimization, SSR, authentication and 3D rendering after any framework/runtime change. Evidence: npm production audit described above.

32. **Medium/High — rebuild the PWA worker with every production release and apply updates safely.** Worker generation depends on BUILD_PWA_SW=true, but the ordinary build script does not set that flag. A checked-in generated worker can therefore reference an older release's chunks. `skipWaiting: true` combines with automatic reload on controllerchange, which can interrupt forms/checkout despite an Apply button. Generate release-matched precache assets, preserve drafts and gate activation on explicit consent or a safe idle point. Evidence: next.config.ts:118; package.json; public/sw.js; sw.ts:26; components/pwa/PwaUpdater.tsx:42.

33. **High operational priority — provide complete recoverable backups.** The button named Complete Backup exports selected in-memory arrays. It omits class enrollments, belt histories, achievements, LMS progress, physical evaluations, body composition, partners, POS/inventory, permissions, audit history, Auth and storage objects. It also inherits truncation from initial loading and uses profileForm, which can contain unsaved edits. Label this as a limited export and implement database/storage backups with a documented, tested restore procedure. Evidence: components/SettingsView.tsx:496; lib/store.tsx:741.

34. **Medium — make schema setup reproducible.** The README refers to supabase/schema.sql, which is absent, and migrations assume core tables already exist. Functions with similar names but VARCHAR/TEXT signatures and changed payload expectations need explicit cleanup/versioning. Several migrations drop only named legacy policies; verify the full effective policy set because permissive policies combine with OR. Build a clean database baseline, ordered migrations, generated database types and automated schema/permission checks. Evidence: README.md database setup; supabase/migrations; PostgreSQL policy semantics: https://www.postgresql.org/docs/current/ddl-rowsecurity.html

**Product and maintenance recommendations**

35. **Improve staff workflows and accessibility.** Use shared dialogs with focus trapping/restoration, appropriate dialog semantics and consistent Escape behavior. Add visible field errors, dirty-form warnings, keyboard-friendly POS/attendance interactions and realistic tablet tests. Keep translations consistent across security, household, receipt and operational messages; update document language with selected locale. These are source-based recommendations; no cross-device visual/accessibility audit was completed.

36. **Add configurable academy operations.** After correctness work, useful features include configurable tuition plans and effective dates, holiday/makeup sessions, waitlists, guardian consent/collection permissions, overdue-payment follow-up, absent-student follow-up, MOU renewal reminders and a daily owner exception list. Preserve staff approval and delivery history for any outgoing notifications. Existing manual links or visible alerts do not establish that background notification delivery exists.

37. **Reduce maintenance cost and improve observability.** Split the approximately 4,500-line global store and large financial/POS screens into domain services and components; generate Supabase types instead of relying extensively on any. Debounce realtime refetch bursts and load only current-module data. Add production error correlation, API latency/failure monitoring, failed-sync counts, migration health and backup-restore checks. The anatomy implementation already includes lazy loading and disposal; measure its real device/download/GPU performance before choosing further optimization.

**Suggested execution order**

1. Secure RPC/profile privileges, enforce effective permissions, remove shared passwords, implement real session revocation and fail-closed login.
2. Repair shop/POS contracts, stock reservation/cancellation, authoritative pricing, transaction boundaries and truthful payment/receipt results.
3. Persist households; unify billing/timezone rules; fix attendance, class capacity, student ID allocation and complete data loading.
4. Repair React errors and release gates; update dependencies; validate PWA release behavior; establish reproducible migrations and restore-tested backups.
5. Improve accessibility, maintenance structure, monitoring and optional academy features.

The most important live follow-up is to inspect installed Supabase grants, functions, RLS policies, storage bucket access and existing-token suspension behavior using controlled test accounts. Until those checks and the urgent correctness fixes are complete, this review does not establish production readiness.
